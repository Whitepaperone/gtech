# COA API

사내 ERP Firebird DB를 SELECT 전용으로 조회하는 Node.js API입니다.

## 로컬 준비

1. Node.js 20 이상을 설치합니다.
2. `.env.example`을 `.env`로 복사하고 실제 값을 입력합니다.
3. `npm install`을 실행합니다.
4. `npm test` 후 `npm start`를 실행합니다.

API 호출에는 `Authorization: Bearer <API_KEY>` 헤더가 필요합니다. `/` 상태 확인만 인증 없이 사용할 수 있습니다.

## Snapshot

기본 저장 위치는 `data/snapshots`입니다. 운영 서버의 기존 폴더를 계속 사용하려면 `.env`에 다음처럼 지정할 수 있습니다.

```text
SNAPSHOT_DIR=shipment_snapshots
```

기존 JSON을 이동하기 전에는 운영 서버에서 API 프로세스를 중지하고 백업해야 합니다.

## 변경사항 처리 이력

`PRODUCTION_PLAN`과 `SHIPMENT_DISPOSAL`은 서로 독립적으로 처리 완료 상태를 관리합니다.
처리 이력은 기본적으로 `data/change_acknowledgements.ndjson`에 저장되며 ERP DB에는 기록하지 않습니다.

## 출고 변경 비교 및 적용

- 어제까지의 출고를 날짜(`DDAY`)·출고번호(`SALESCODE`)·품번(`ITEMCODE`)으로 묶어 `QTY` 합계를 비교합니다. 합계가 같으면 행 분할, 고객사 및 기타 속성 변경은 알리지 않습니다.
- 키 변경은 기존 묶음 삭제와 새 묶음 추가로 기록합니다. 신규 묶음에는 원본 세부 행(`SOURCE_ROWS`)을 포함하여 엑셀에 원래 행 단위로 입력합니다.
- 같은 날에도 마지막 조회 시 저장한 스냅샷과 비교합니다. 최초 스냅샷이 없으면 기준만 생성합니다.
- 감지한 변경은 스냅샷 폴더의 `change_events.json`에 먼저 저장합니다. 각 consumer의 처리 완료 전까지 다음 조회에서도 반환하며, 날짜가 지나도 유지합니다.
- `ShipmentChanges.py`는 수정·삭제 묶음의 기존 행 전체를 표시하고 `출고변경내역` 시트에 이전/현재 합계 및 증감을 기록합니다. 기존 행이 없어도 내역을 기록하고 저장 성공 후 처리 완료합니다. 기존 수량 및 수식은 자동 보정하지 않습니다.
- 결과 파일의 변경ID로 재입력을 방지합니다. 처리 완료 후에는 저장된 결과 파일을 다음 작업의 입력으로 사용해야 합니다.

적용 시 서버 코드와 클라이언트를 함께 교체하고 API를 재시작합니다. 기존 스냅샷 JSON은 그대로 읽을 수 있습니다. 스냅샷 폴더(이벤트 파일 포함)와 처리 완료 로그를 함께 백업·보존하세요. 과거에 이미 비교 기준에서 사라진 삭제 건은 새 이벤트 저장만으로 복원되지 않습니다. 파일 기반 저장이므로 API는 단일 프로세스로 실행합니다.
